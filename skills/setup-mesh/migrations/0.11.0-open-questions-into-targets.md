# 0.11.0 — open questions move into the file they are about

**Applies when:** the Hub root, or any domain folder, has a `staging/open-questions.md`.
**Guard:** no such file anywhere in the mesh means this is already migrated — say so and move
on. A file that exists but is empty (no question content, only a heading or template text) is
also a no-op: report it as safe to delete, and delete nothing.
**Requires:** —
**Precedes:** —

## What changed

An unresolved question used to live in a central `staging/open-questions.md`. It now lives in
an **`## Open questions` section of the context file it is about** — a question about runtime
behaviour goes in `technical/system-behavior.md`.

Three reasons:

- **Progressive disclosure works.** Whoever loads a file to reason about its subject sees that
  something in it is unsettled. In a central list they would only find it by loading a file
  about everything.
- **It reuses a decision already made.** "Which file is this about?" is what routing answers.
  A separate questions file asks it a second time, with a second chance to get it wrong.
- **Resolution stops being a move.** The question already sits in the right file, so resolving
  it edits it in place.

The cost, stated plainly: *"what is unresolved across the whole mesh?"* is now a grep rather
than one file read. The `## Open questions` heading is a fixed convention so that grep is
reliable.

`OpenQuestion` as a **node type is unchanged**, and so is promotion's `RESOLVE` outcome. Only
where the text sits changed.

## What this migration does

**It reports. It moves nothing.**

`staging/open-questions.md` is human-authored content — often the only record of a question
someone raised — and this migration cannot know which context file each question belongs to.
That is a routing decision, and routing is a human-validated step in this system. Guessing it
would be the plugin deciding where someone else's content goes.

So, for each `staging/open-questions.md` found:

1. **Report its path and how many questions it appears to hold.** Count conservatively — list
   items or headings. If the shape is unclear, say the file has content and do not guess a
   number.
2. **Name the convention:** each question moves into an `## Open questions` section of the
   context file it concerns, and the file is then deleted by the human.
3. **Do not edit or delete the file.** Do not create `## Open questions` sections anywhere.
   Do not attempt to route individual questions.

**The index needs no change.** `staging/open-questions.md` was never an index row — the
Staging table names staging locations as backticked text, not as linked context homes — so
there is no row to remove. If a hand-authored index *does* link it, report that as a row to
remove by hand rather than editing it, since a linked staging path is a hand-authored claim
whose intent this migration cannot know.

## The one thing to tell the human

**Nothing is lost and nothing is broken right now.** A mesh with a leftover
`staging/open-questions.md` keeps working: the file is still readable, and ingestion never
routed to it. What changes is where *new* questions land, so the old file will simply stop
growing while the new sections start.

Say that plainly, because the natural reading of "a migration applies to your mesh" is that
something is now wrong. It isn't. This is a convention change with a manual step, and the
manual step is deliberate: whoever raised those questions knows which file each belongs in,
and the plugin does not.
