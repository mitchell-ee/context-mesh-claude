# 0.3.0 — remove the workflow layer from indexes

**Applies when:** any `context-index.md` in the Hub has a `## Workflows` section, or a
context-table row pointing into `process/workflows/`; or any staged candidate declares
`type: Todo`, `type: Task`, or `type: Workflow`, an edge `routed-to` / `triggers` /
`creates`, `state: resolved`, or the `HANDOVER` verb.
**Guard:** an index with no `## Workflows` section and no `process/workflows/` row is
already migrated — skip it. If no index in the Hub has either, this migration is a no-op:
say so and move on.
**Requires:** —
**Precedes:** —

## What changed

Vocabulary v2.2 deferred the workflow layer out of the schema. `Todo`, `Task`, and
`Workflow` are no longer node types; `routed-to`, `triggers`, and `creates` are no longer
edges; `state: resolved` and the `HANDOVER` promotion verb are gone.

The reasoning: **the mesh holds context, not work.** A queue is not context — it is the work
itself. Every team tracks work differently, and that content is a different *kind* of thing:
transient and in-flight, where context is decided and durable. Ingestion still *notices*
action items and reports them; it just does not file them.

The design is retained privately and may return as a future feature.

## What this migration does

**It edits indexes. It does not touch anything else.**

Specifically:

1. **Remove the `## Workflows` section** from every `context-index.md` that has one —
   heading, explanatory comment, and table.
2. **Remove context-table rows whose path points into `process/workflows/`.**

That is all. In particular:

- **`process/workflows/` and everything in it stays exactly where it is.** The directory is
  not deleted, not moved, not emptied. A team's `backlog.md` pointing at their Jira board is
  content someone wrote; the mesh no longer has a home for it, which is a reason to stop
  *referencing* it, not a licence to remove it.
- **Staged candidates using the deferred types are left in place.** Report them; do not
  rewrite them. A candidate is a proposal awaiting a human gate, and re-typing someone's
  proposal is a routing decision the migration is not entitled to make.

## Procedure

1. **Find every index in the Hub** — the root `context-index.md` and each
   `domains/*/context-index.md`.
2. **For each, check for the two shapes**: a `## Workflows` heading (v2.1 wrote it as
   `## Workflows (routable processes)`, so match the heading prefix, not the whole line), and
   any context-table row whose path contains `process/workflows/`.
3. **Show the human exactly what would be removed**, per file, before removing anything.
4. **On approval, remove those sections and rows.** Leave the rest of the index untouched —
   identity, load conditions, and every other row are the team's.
5. **Report what is now unreferenced.** For each index that had workflow rows, say which
   files under `process/workflows/` are no longer pointed at by anything, and that they
   remain on disk. This is the part the human acts on: those files are now orphaned as far
   as the mesh is concerned, and only they can decide whether that content moves to a work
   tracker, stays as an unrouted note, or is deleted by hand.
6. **Report any staged candidate** using a deferred type, edge, state, or verb — by path,
   with what it declares. Changed by hand or not at all.

## The trap to avoid

**Match on structure, never on the bare word.** `Workflow` inside a sentence — "our review
workflow is documented elsewhere" — is prose in someone's context file and must be left
alone. What this migration matches is:

- a heading that starts `## Workflows`
- a table row whose **path** contains `process/workflows/`
- a frontmatter `type:` / edge key / `state:` field in a candidate

A blanket text substitution on the word "workflow" would keep finding new things to fix on
every run, which is the opposite of idempotent, and would corrupt prose it has no business
touching.

## Idempotence

Guarded on the presence of a `## Workflows` section or a `process/workflows/` row. Once
those are gone from an index, a re-run matches nothing there and does nothing. Because the
migration never touches `process/workflows/` itself, the directory's continued existence is
**not** a trigger — a mesh that keeps those files forever is fully migrated as long as no
index points at them.
