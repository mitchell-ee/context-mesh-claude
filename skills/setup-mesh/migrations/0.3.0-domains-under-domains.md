# 0.3.0 — domains moved under `domains/`

**Applies when:** a directory at the Hub root, outside `domains/`, holds a
`context-index.md`.
**Guard:** if every index in the Hub is either the root's own or under `domains/`, this
migration is a no-op — say so and move on.
**Requires:** —
**Precedes:** —

## What changed

Through v2.1, domains sat at the Hub root beside the cross-cutting folders, and the tooling
had to **guess** which top-level directories were domains — it accepted anything containing a
`product/`, `technical/`, or `process/` subdirectory. In the first third-party run that
heuristic reported a `docs/product/` market-research folder as a domain and printed scaffold
instructions for it, while the repo's actual product tree went undetected because it had no
such subdirectory. The heuristic found the wrong one of the two.

v2.2 made a domain **exactly a directory under `domains/`**, and nothing else. The path is
the declaration, so nothing has to detect domain-ness. That deletes the problem class rather
than tuning it: no ignore list, no detection rule, nothing to misfire.

## Why this migration only reports

**It moves nothing.** This is the strictest case of the rule in `README.md` — the plugin only
ever adds to the mesh.

A migration that moved root-level directories into `domains/` would be doing exactly what
v2.2 deleted: **deciding what is a domain**. It cannot know. A root-level directory holding
an index might be a domain from a v2.1 mesh, or a documentation tree someone gave an index
to, or a folder that predates the mesh entirely. Guessing wrong relocates a team's content
into a namespace where routing will then write to it.

So the migration states a fact about **visibility**, which it can verify, and leaves the
question of **identity**, which it cannot, to the human:

> `payments/` holds a `context-index.md` but is not under `domains/`, so routing cannot see
> it. If it is a domain, move it. If it is not, ignore this.

## Why the detection is narrow

This migration keys on **`context-index.md` being present**, not on subdirectory shape. That
matters: an index is something a person *wrote for this mesh*, so finding one outside
`domains/` is worth mentioning. A bare `docs/product/` folder is not evidence of anything,
and must stay silent — reporting it is the exact false positive v2.2 removed.

`survey_mesh.py` implements this check and prints it on every run, so the finding surfaces
whether or not anyone is running migrations.

## Procedure

1. **Run the survey** — `survey_mesh.py <hub-root>` reports every root-level directory
   holding an index, under `CONTEXT ROUTING CANNOT SEE`.
2. **For each, ask the human what it is.** Do not propose an answer for a directory whose
   name does not make it obvious, and do not treat "it has technical/ and product/ subdirs"
   as evidence — that is the deleted heuristic.
3. **For each one they confirm is a domain**, tell them:
   - `git mv <name> domains/<name>` — by hand, so history follows and they can see it.
   - Add a row to the root index's `## Domains` table.
   - Re-run the survey to confirm it now appears as a domain.
4. **For each one they say is not a domain**, do nothing at all. It is content that lives in
   the repo without being part of the mesh, which is legitimate.
5. **Never run the move.** Even with confirmation. The human moving their own content is the
   point — the migration's job is to make the invisible visible.

## What breaks if this is skipped

Nothing silently corrupts, but two things go wrong quietly, which is why the survey reports
it on every run rather than only during migration:

- **The domain's context is invisible to routing.** Ingestion cannot route a fact to it, and
  will report the fact as having no home.
- **Setup will scaffold an empty duplicate.** `scaffold_domain.py <hub> payments` checks
  `domains/payments/`, which does not exist, so it creates it — leaving two same-named
  domains, one real and orphaned, one empty and indexed. Routing reads the empty one.

The second is the reason this cannot wait for someone to notice: the idempotence guard that
normally makes re-running setup safe does not protect against it, because it is checking a
different path.

## Idempotence

Guarded on a root-level directory holding an index. Once the human has moved it under
`domains/`, there is nothing at the root to find, and a re-run reports nothing. Because the
migration never moves anything itself, running it twice is trivially safe — the second run
prints the same report, or none.
